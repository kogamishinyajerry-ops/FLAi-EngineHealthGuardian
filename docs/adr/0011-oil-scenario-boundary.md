# ADR 0011 — 第三个场景(滑油)与边界的真义

- 状态:Accepted
- 日期:2026-08-12

## 背景
MVP 要 3–5 场景;已有 EGT、振动。再加一个滑油场景,第三次压测「加场景不动库」,并刻意用**不同的特征形状**(消耗速率)来更狠地压边界。

## 这次为什么不同
EGT/振动是「单快照残差 vs 物理 baseline」,适配通用 `PeerGroup`。滑油**消耗**是从油箱液位差分得出的**速率**,**不适配**逐快照的 `PeerGroup` —— 所以本场景自带「机队速率 peer」(各发动机的平均消耗率 vs 机队),而不是硬套通用件。这恰好暴露了边界在「不同特征形状」下的真实表现。

## 发现:边界需要一次「共享词缀扩展」
滑油观测(温度/压力/液位)在 `EngineSnapshot` 里没有字段。这不是「场景逻辑」,是**共享数据词缀**;新物理域需要扩展它。

**唯一库改动**:`EngineSnapshot` 加 `oil_temp_c` / `oil_pressure_kpa` / `oil_level_l`(可选,向后兼容)。**除此之外零库逻辑改动**:复用 `residual_trend` / `uncertainty` / `policy.gate` / `Evidence` / `run_agent` / `AuditLog`;特征工程 + 机队速率 peer 全在 `scenarios/oil/`。

## 决策与边界真义
边界的真义不是「永远零库改动」,而是:
- **场景逻辑(特征/规则/管线)留在 `scenarios/`**(滑油做到了)。
- **共享词缀/原语的扩展是协调式改动**(滑油只动了 `EngineSnapshot` 词缀,没动任何脑的逻辑)。

把「零库改动」当教条是错的 —— 新物理域天然需要新词缀。真正的检验是:**场景逻辑没有泄漏进库**。

## 后果
- 好:MVP 达到 3 场景;边界在不同特征形状(速率)下仍成立;滑油词缀为后续(油温/油压特征)留了字段。
- 教训:第三次压测的最大收获不是「又证明了一次」,而是**澄清了边界的定义**(逻辑隔离 ≠ 词缀冻结)。
- 仍是占位:油泄漏判定是合成数据 + 占位阈值;油温/油压特征 deferred(字段已就位)。
